# Torrents and magnets: implementation and limits

**Next-build source contract, not a cross-platform verification report or a description of the already-published 0.0.1-pre.0 assets.** The UI-independent core automatically detects v1, BEP 52 v2 and hybrid metainfo. Default v1 uses pinned Apache-2.0 `librqbit` 9.0.1; v2/hybrid and opt-in advanced v1 settings use a separate BSD-3-Clause libtorrent 2 native process. V2 is not a toggle on the v1 client. Ulos remains MIT. Redistributors must retain engine/runtime licenses and notices, including the supplied libtorrent BSD/component notices, OpenSSL Apache-2.0, Boost-1.0 and nlohmann-json MIT files in `packaging/licenses/`; this is not a completed transitive license audit. See [Research](RESEARCH.md), [packaging](../packaging/README.md) and the [testing plan](TESTING.md).

## Engine selection and consent

- Opening/parsing is offline. Format/backend selection is automatic, **upload permission is not**. V2/hybrid requires explicit **Allow peer uploads while downloading** consent and an available bundled worker; otherwise Start is blocked. There is no silent v1 fallback for v2/hybrid.
- Unchanged v1 defaults retain tracker-only discovery, compile-time/runtime payload-upload denial and a 40-peer rqbit cap. The shared native-settings default of 100 peers does not change that legacy cap.
- Opting into peer uploads selects the native engine, including for v1. Public DHT, initial download/upload rates and peer limit require that engine and upload consent. The worker cannot guarantee hard no-upload; zero upload rate means unlimited, not disabled. Payload uploads can occur during download only; no post-completion seeding mode is implemented.
- Private torrents always disable DHT (and native PEX/LSD); the review disables the DHT choice and rejects an invalid private-DHT combination. Public DHT is optional, default off. LSD, UPnP/NAT-PMP port forwarding and resume persistence remain unimplemented/disabled. Magnet-resolution DHT is a separate default-off opt-in described below; private status is not yet known at that stage.
- Review uses stock Kit Checkboxes/Inputs for consent, DHT and initial limits. Details → Speed provides real **Apply rates** and **Apply peers** controls for consented native transfers: paused transfers accept live changes; queued/retry settings apply next start. Rates are 1–1,048,576 KiB/s, blank for unlimited; peer limit is 1–10,000. Unsupported v1/no-consent combinations fail honestly, never simulate live controls. These bounded settings do not promise wire-speed QoS, unlimited resources, peer availability or completion.

## Intake and shared workflow

- **Add New → HTTP URL / Torrent file** offers separate native review windows. Picker, manager drag/drop, startup native paths/local `file://` URLs and OS-open callbacks all require confirmation. At most 16 raw file proposals per batch and 16 live Add drafts combined; paths/URL text are bounded to 16 KiB, argv to 18 tokens. Stable deduplication preserves native path encoding, including supported non-UTF8 local paths. Remote file hosts/UNC syntax, malformed URLs and unknown opener options fail closed. Lexical intake is not proof of file existence or local storage.
- Review name, total bytes, file count/manifest (first 20 displayed), tracker count, destination and collision policy offline. No session/tracker/peer is created by parsing, opening or dropping a file. **Start download** explicitly dispatches when idle; **Download later** does not enable a stopped queue, but confirmation allows an already-running queue to dispatch the item.
- HTTP/torrent records share the existing category sidebar and queue table, appending **Type** after Description, with no torrent sidebar group or dedicated torrent destination folder. Single-file torrents use their payload filename's existing category; multifile torrents use Other.
- One global active slot, named queues, explicit ordering, session scheduler and completion gates cover both protocols. Paused work holds the slot. Actual engine Pause/Resume is asynchronous: command acceptance is not observed Paused state. Native rate/peer controls are separate from HTTP range-worker controls and require upload consent. Progress/phase/peer/upload counters come from the engine; initializing scan bytes are not reported as verified download progress.

## Explicit magnet metadata resolution

The Torrent file draft provides a stock **Magnet link** Input and **Resolve magnet** Button. The public Rust API is `ulos_core::torrent::{validate_magnet, resolve_magnet}`: validation is offline; awaiting resolution is an explicit networking operation requiring the native worker even for v1. Typing/pasting, clipboard detection and opening a draft never auto-resolve; there is no OS `magnet:` registration or magnet argv/open association. Successful resolution only populates review. **Start download** or confirmed **Download later** is a separate payload decision; no resolver result automatically creates a queue item or downloads payload.

The accepted URI subset is at most **16 KiB**, with one `xt=urn:btih:` (40 hex or 32 base32 digits), one `xt=urn:btmh:1220` followed by a 64-hex SHA-256 digest, or both for hybrid identity. Optional `dn`, up to **64** HTTP/HTTPS/UDP `tr` trackers and **64** numeric `x.pe` socket addresses are supported. Invalid/duplicate identities, malformed escaping, unsafe trackers/peers and all unknown parameters (including `ws`/`xs` webseed/exact-source extensions) fail closed; names/URLs remain bounded and display names are advisory, never a replacement for the verified manifest.

Resolution contacts configured trackers/direct numeric peers only after **Resolve magnet**. The separate **Allow public DHT during magnet resolution** Checkbox starts off, independently of payload DHT/upload consent. **Private status is unknown before metadata is discovered: opting into public DHT may expose a private torrent's hash.** No hidden privacy guarantee is made; trackers/peers also learn network address/infohash. Once metadata identifies a private torrent, its payload review disables DHT under the normal policy.

`torrent_magnet.rs` owns a shell-free native `--resolve-magnet` process with a private temporary directory, a **120-second engine** deadline and **125-second host** deadline. The resolver sets file priorities to zero and `upload_mode`, obtaining metadata without automatic payload transfer. This metadata-only mode is not a hard no-protocol-traffic guarantee or a substitute for payload-upload consent. Bounded IPC, successful child exit/teardown, exact requested infohash matching and the core metainfo parser (including SHA-256 piece-layer/root checks) precede review. Timeout, malformed/mismatched metadata and process failures produce redacted errors. Cancellation/drop requests owned child teardown/reaping and temporary cleanup; keep the caller runtime alive until cleanup finishes, not merely until the resolving future is dropped.

BEP 9 metadata does not carry BEP 52's required top-level piece layers. **V2/hybrid magnets with any file larger than one piece therefore fail closed** when those layers are missing: use a `.torrent` file containing them. Small v2/hybrid metadata that requires no such layers can resolve. Ulos never fabricates proof layers from payload or treats unavailable layers as verified. This is bounded magnet support, not every-magnet support or guaranteed peer availability.

## Live diagnostics

The source-level diagnosis addresses a reported **0 B / Downloading** view with hidden peer/rate information; it does not establish that the user’s torrent was repaired or downloaded. The stock Kit **Status** summary always exposes **Peers** (connected, connecting, queued), **Download speed**, **Upload speed** (zero under the default no-upload policy), and **Trackers** (configured count), independently of the details disclosure. These are real observations, not decorative panels or new controls.

Download/upload rates come from the selected engine. Native libtorrent supplies payload B/s directly; librqbit 9.0.1’s `mbps` value is **MiB/s**, converted to **B/s** by multiplying by 1,048,576; invalid/nonpositive samples become zero. Verified piece bytes remain separate, so an incomplete piece can have a nonzero payload rate while verified progress stays at 0 B. Initial checking/scanning is not downloaded progress. Active downloading peer/rate presentation is gated by `snapshot.torrent_fresh` (a sample younger than two seconds); stale live values are withheld as unavailable, not inferred zeros. Paused, publishing and terminal activity is zero, not a retained last speed. Missing telemetry remains unavailable.

Downloading-phase labels follow observed activity, in this order:

| Label | Observation |
| --- | --- |
| No peer discovery | Neither configured trackers nor enabled DHT, and no connected, connecting or queued peers; discovery has no source. |
| Connecting to peers | No connected peers, but connecting or queued candidates exist. |
| Searching for peers | No connected or pending candidates; configured trackers do not establish successful discovery. Previously seen peers may no longer be available. |
| Stalled | Connected peers, with neither fetched payload bytes nor verified piece bytes changing for at least 15 seconds. |
| Waiting for peers | Connected peers, but no initial verified bytes or current payload rate, before the stall threshold. |
| Downloading | Otherwise, normal downloading activity. |

Preparing, Checking, Paused and Verifying / publishing retain their own phases. The monotonic stall monitor resets on fetched/verified movement and phase transitions; time paused is not downloading stall time.

**Trackers configured is neither successful announce count nor seed count.** Peer counts and peers-seen observations (historical for rqbit, current known list for native) cannot prove tracker failure, choking, or seed/live availability; explanations describe possibilities, not diagnoses of remote systems. No tracker URLs, signed queries or peer addresses are exposed/logged for this diagnosis. Diagnostics reflect the selected upload/DHT policy; they never enable either to make progress. Default v1 remains tracker-only/no-upload; consented native public torrents can use DHT. Local discovery stays off. No user torrent or public network was used for this diagnostic change, and no new native screenshot or live-user download result is claimed. Local-fixture and native review requirements are in the [testing plan](TESTING.md#torrent-verification-plan-not-results); actual command outcomes are recorded separately.

## Offline metainfo profile

Accept bounded v1, BEP 52 v2 file trees/piece layers and matching hybrid v1/v2 manifests. SHA-256 piece-layer roots/counts and padding subtrees are validated offline. Hybrids must agree on real paths/lengths and valid aligned v1 padding; padding is virtual zero bytes, not a published payload file. Zero-length regular entries are retained within an overall nonzero torrent. Strict parsing still rejects unsupported encodings, symlinks and malformed/unsupported extensions; this is not every legal torrent. Magnet results must pass this same parser; they do not bypass piece-layer validation. Raw `url-list`/`httpseeds` declarations are rejected before either engine parses them, including empty/malformed webseed fields.

The regular-file worker read is capped at **8 MiB**. Before engine deserialization the strict bencode parser bounds depth to **32**, nodes to **65,536**, file count to **4,096**, and piece count to **262,144**. Piece length must be a power of two from 16 KiB through 64 MiB; piece count must match the nonzero checked total (at most `i64::MAX`). Dictionaries must be canonical/unique; negative integers and trailing data fail. Limits bound metadata, not required payload disk capacity.

Path validation is reject-only, not silent manifest rewriting: portable UTF-8 components up to 180 bytes, at most 32 components and 2,048 native path units, no traversal/absolute paths, separators, reserved/unsafe names, symlinks or ambiguous alternate UTF-8 fields. Only validated hybrid alignment padding is allowed as virtual zero bytes, never real output. NFC normalization plus full Unicode case folding rejects duplicate and file/directory-prefix conflicts across case-insensitive filesystems. The engine-decoded manifest must exactly match approved paths and lengths. Ancestor paths must not be modified by a hostile local process; this is not a filesystem sandbox.

## Networking and privacy

For `.torrent` payload transfers, approved HTTP/HTTPS/UDP trackers are contacted only on dispatch (at most 64 entries, each at most 4,096 bytes). Embedded credentials/fragments and unsupported schemes fail; signed queries are preserved in memory for operation, never displayed/logged or stored in history. `TorrentSource` has no Debug representation; errors are redacted and rqbit-owned threads suppress sensitive tracing. Trackers, peers and optional public DHT can observe network address/infohash; this is not anonymity. Upload denial does not mean zero outbound announces, handshakes or protocol bytes and may prevent progress in reciprocal swarms. No user torrent or public tracker/DHT network is used for acceptance testing.

Rqbit defaults are disabled, with `rust-tls` / `disable-upload` and session upload denial. DHT, local discovery, inbound listeners, UPnP, persistence, HTTP serving and seeding are off on that path. The native payload worker permits uploads only after consent; LSD, UPnP/NAT-PMP and persistence stay off, and private torrent DHT/PEX stay off. Native operation is not a no-inbound-listener guarantee.

## Native process boundary

`torrent_native.rs` launches the bundled worker by absolute path, without a shell, with piped protocol-1 JSON-lines and ignored stderr. It validates engine major/version, exact original approved file paths/lengths, privacy and all applicable infohashes before sending **Start**. The worker parses and emits its manifest **without constructing a session**; there are no tracker/peer/DHT sockets until Start in this payload mode. The separate explicit magnet-resolution mode creates a metadata-only session after Resolve, as described above. Engine-sanitized names are never substituted for approved paths. IPC has bounded frames, command sizes/batches and a handshake deadline; malformed events, missing helpers and child failures fail closed with redacted errors. Cancellation/EOF tears down the process; completion requires a successful child exit after synchronous engine teardown. Packaging availability checks are not proof that a helper can launch or its libraries resolve.

## Ownership, integrity and publication

Each dispatched task owns unique `.ulos-torrent-*` staging beside the selected destination. Rqbit uses a private Tokio runtime; the native engine uses an owned child process. The session/runtime or process is stopped and joined/reaped before verification/publication/cleanup. Final verification independently checks the exact approved tree, regular-file sizes and all applicable hashes: full v1 SHA-1 piece streams (including cross-file pieces), v2 per-file SHA-256 Merkle roots, and both for hybrids with virtual zero padding in the v1 stream. Engine completion/resume claims are not trusted as integrity proof; no fast-resume trust is introduced. Each file is then synced. An infohash identifies metainfo, not an HTTP strong validator or independent authenticity proof.

**Reject / Rename only; Overwrite is rejected before networking.** Single files publish by no-clobber hard link; multifile directories use no-replace rename on macOS/Linux and `renamore::rename_exclusive` (`MoveFileExW` with no flags) on Windows. Rust standard-library Windows rename is not used because its fallback permits replacement. Rename tries the original and up to 1,000 bounded numbered candidates. Existing data, late collisions, symlinks and directories are never intentionally replaced. Native filesystem semantics still require platform testing. Completed is emitted only after successful publication and carries its actual path; completion shutdown cannot treat engine-finished alone as success.

Cancellation is checked between directory entries, files and bounded hash-read chunks; an individual blocking filesystem call cannot itself be interrupted. After teardown, staging cleanup is explicit. A cleanup failure before publication reports a redacted cleanup error; cleanup failure after publication preserves the successful receipt and can leave staging remnants. Publication already underway can win a cancellation race. Drop only requests cancellation, so the caller must retain the outer runtime until terminal observation. Abrupt termination can leave staging; no restart/checkpoint recovery is implemented.

## History, removal and packaging

SQLite history schema **v2** adds protocol/directory flags alongside metadata; it stores no raw torrent, source path/URL or tracker query. Restored source-less rows cannot start or retry. Named queues/schedules remain session-only. Multifile directory removal is metadata-only; Ulos does not recursively delete a completed payload directory.

Development packaging lives in [packaging](../packaging/README.md). `scripts/bundle-macos.sh` copies already-built desktop/mandatory worker/runtime libraries/notices into an absent `.app`, with imported `org.bittorrent.torrent` UTI and Viewer/Alternate document role; it applies ad-hoc integrity signing, but does not launch/register/notarize/install, Developer ID–sign or change defaults. Linux's desktop entry advertises `application/x-bittorrent` / `%F` Open With. Windows's deliberately invoked per-user HKCU Open With registration script does not set UserChoice/defaults or machine keys. No Windows registration script was executed for this update. File associations are packaging declarations, not automatically installed or selected defaults, and do not prove native OS launches. Native association/open/drop, accessibility and clean-install validation remain pending.

Only transfer content you have permission to obtain. No DRM, captcha or access-control bypass is provided.
